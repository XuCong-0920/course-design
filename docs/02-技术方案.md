# 技术方案（主 App · B4 单词记忆）

## 1. 架构分层

```
UI (Fragment + ViewBinding)
  ↓ 事件 / StateFlow
ViewModel（状态持有，无 Android Context 依赖）
  ↓
Repository（WordRepository / ReviewRepository / SettingsRepository）
  ↓
Room DAO  ·  DataStore  ·  SAF 文件读取  ·  WorkManager
```

- 单 Activity + Navigation（`res/navigation/nav_main.xml`），页面间用 `Bundle` 参数传参
  （未引入 SafeArgs 插件：AGP 9 + 内置 Kotlin 下少一个插件少一层坑，参数名以 `companion object` 常量约束）。
- 依赖注入：先手写单例（`WordMemoryApp` 持有 `WordDatabase` / `WordRepository`，Fragment 通过 `Application` 取用），避免过早引入 Hilt。
- 线程：Room/文件 IO 走 `Dispatchers.IO`（Room 的 `Flow` 查询本身在 Room 的执行器上）；算法为纯 Kotlin，可在 JVM 单元测试中直接测。

## 2. 数据模型（Room，已落地）

数据库 `word_memory.db`，version = 1，`exportSchema = false`，三张表：

```kotlin
@Entity(tableName = "decks")
data class DeckEntity(
    @PrimaryKey(autoGenerate = true) val id: Long = 0,
    val name: String,
    val description: String = "",
    val createdAt: Long = System.currentTimeMillis(),
)

@Entity(
    tableName = "words",
    foreignKeys = [ForeignKey(DeckEntity::class, ["id"], ["deckId"], onDelete = CASCADE)],
    indices = [Index("deckId"), Index(value = ["deckId", "term"], unique = true)],
)
data class WordEntity(
    @PrimaryKey(autoGenerate = true) val id: Long = 0,
    val deckId: Long,
    val term: String,          // 单词（同一词库内唯一）
    val meaning: String,       // 释义
    val phonetic: String = "", // 音标
    val example: String = "",  // 例句
    // ---- 内嵌 SRS 状态 ----
    val repetition: Int = 0,   // 连续答对次数
    val intervalDays: Int = 0, // 当前间隔天数，0 = 新词
    val easeFactor: Double = 2.5,
    val dueAt: Long = System.currentTimeMillis(), // 下次到期时间
    val lastReviewedAt: Long? = null,
    val createdAt: Long = System.currentTimeMillis(),
)

@Entity(tableName = "review_records")
data class ReviewRecordEntity(
    @PrimaryKey(autoGenerate = true) val id: Long = 0,
    val wordId: Long,
    val grade: Int,            // 0 不认识 / 1 模糊 / 2 认识
    val intervalDaysAfter: Int,
    val reviewedAt: Long = System.currentTimeMillis(),
)
```

设计取舍：

- **SRS 状态内嵌在 `words` 行内**，不另建状态表：复习队列只需 `WHERE dueAt <= :now` 一次索引扫描，
  避免每张卡片再 JOIN 一张状态表。
- **`(deckId, term)` 唯一索引**：重复导入同一词库时用 `OnConflictStrategy.IGNORE` 天然去重。
- **到期计数用子查询**（`DeckDao.observeSummaries`），列表页一次查询拿到「词库 + 单词数 + 今日到期数」，
  不在 UI 层做 N+1 统计：

```sql
SELECT d.id, d.name, d.description,
       (SELECT COUNT(*) FROM words w WHERE w.deckId = d.id) AS wordCount,
       (SELECT COUNT(*) FROM words w WHERE w.deckId = d.id AND w.dueAt <= :now) AS dueCount
FROM decks d ORDER BY d.createdAt ASC;
```

- **种子数据**：`SeedData` 内置「B4 结课词表」12 词与「四级高频」10 词；`WordRepository.ensureSeeded()`
  在 `Application.onCreate` 的 IO 协程里执行，`deckDao.count() > 0` 直接早退，写入包在
  `database.withTransaction { }` 里，保证「词库 + 其下单词」不会出现半截数据。

## 3. SRS 调度算法（自定义，核心评分点）

简化 SM-2，三档反馈映射为质量分 q：不认识 = 2，模糊 = 3，认识 = 5。

**实现**：`app/src/main/java/com/xucong/wordmemory/domain/srs/SrsScheduler.kt`，纯 Kotlin、零 Android 依赖，
时间由调用方以 `now: Long` 注入（不读 `System.currentTimeMillis()`），因此可以断言「跨闰日」这类精确时刻。

```kotlin
data class SrsState(
    val repetition: Int = 0,
    val intervalDays: Int = 0,
    val easeFactor: Double = SrsScheduler.DEFAULT_EASE_FACTOR,
    val dueAt: Long = 0L,
)

object SrsScheduler {
    const val DEFAULT_EASE_FACTOR = 2.5
    const val MIN_EASE_FACTOR = 1.3
    const val MAX_EASE_FACTOR = 2.8
    const val MAX_INTERVAL_DAYS = 180
    const val FORGOT_RETRY_MILLIS = 10 * 60 * 1000L   // 答错 10 分钟后再来
    const val DAY_MILLIS = 24 * 60 * 60 * 1000L

    fun schedule(state: SrsState, grade: ReviewGrade, now: Long): SrsState
}
```

规则：

| 输入 | repetition | intervalDays | easeFactor | dueAt |
| --- | --- | --- | --- | --- |
| 不认识（q=2） | 0 | 0 | −0.2（下限 1.3） | now + 10 分钟 |
| 模糊（q=3） | +1 | 1 → 3 → round(旧间隔×旧EF) | −0.14 | now + 间隔 |
| 认识（q=5） | +1 | 1 → 3 → round(旧间隔×旧EF) | +0.1（上限 2.8） | now + 间隔 |

- 间隔统一 `coerceIn(1, 180)`：上限 180 天防止「背熟了就再也见不到」；下限 1 天防止同一天反复刷。
- EF 变化用 SM-2 原式 `EF += 0.1 - (5-q)*(0.08 + (5-q)*0.02)`，并保留两位小数（数据库存 Double，避免浮点噪音）。
- **算法层不认识 `WordEntity`**：`SrsState` 是纯粹的调度状态，`WordEntity` 与它的互相转换放在数据层
  （`WordRepository.submitReview`），这样算法既能在 JVM 单测里跑，也不把 Room 拖进 domain 包。
- 单元测试：`app/src/test/java/com/xucong/wordmemory/domain/srs/SrsSchedulerTest.kt`，11 个用例全绿
  （首次/第二次/第三次答对、答错重置、模糊 EF、EF 上下界、180 天上限、跨闰日、同日重复、三档 DB 值映射）。
  运行：`./gradlew :app:testDebugUnitTest`。

**落库**：`WordRepository.submitReview(word, grade, now)` 在**同一个 `withTransaction`** 里更新 `words`
的 SRS 字段并插入 `review_records`；两者必须同生共死，否则会出现「统计显示背过、调度却没推进」的不一致。

## 4. 通知与后台任务（强制技术点）

已落地（`app/src/main/java/com/xucong/wordmemory/notification/`，WorkManager 2.12.0）：

- **每日提醒**：`PeriodicWorkRequestBuilder<ReviewReminderWorker>(1, DAYS)`
  + `setInitialDelay(到下一个 HH:00 的毫秒数)`，`enqueueUniquePeriodicWork(..., ExistingPeriodicWorkPolicy.UPDATE)`，
  因此重复调用是幂等的，不会叠出多条提醒。
- **为什么用 WorkManager 而不是 AlarmManager**：周期任务在重启/杀进程后由 WorkManager 自行恢复，
  不需要处理 `BOOT_COMPLETED`，也不用申请 `SCHEDULE_EXACT_ALARM`；代价是可能被系统推迟几分钟——
  对「每天提醒背单词」完全可接受。需要分钟级精度时再退化到 `setExactAndAllowWhileIdle`。
- **不打扰策略**：Worker 里先查 `countDue(now)`，**到期为 0 就不发通知**（空提醒最容易被用户顺手关权限），
  再检查「今天是否已点过免打扰」。
- **通知三个 Action**：
  | Action | 实现 | 行为 |
  | --- | --- | --- |
  | 去复习 | `PendingIntent.getActivity` + `EXTRA_OPEN_REVIEW` | 打开 App 并由 `MainActivity` 直接选中复习页 |
  | 10 分钟后 | `PendingIntent.getBroadcast` → `ReminderActionReceiver` | 撤掉当前通知，入队 10 分钟延迟的一次性任务 |
  | 今天不提醒 | 同上 | 写入「今日跳过」标记并撤掉通知，周期任务保留，明天照常 |
- **权限与降级**：`AndroidManifest` 声明 `POST_NOTIFICATIONS`，`MainActivity` 在 Android 13+ 首次启动时申请；
  `ReminderNotifications.canPost()` 统一判断「权限 + 系统通知总开关」，未授权时不弹通知但**不影响任何功能**，
  「我的」页显示红色提示文案（验收要演示的降级路径）。
- **可演示性**：「我的」页提供「立即发一条测试提醒」，避免为演示通知而等到设定时刻。
- **静态存储**：提醒开关/时间/跳过日期用 `SharedPreferences`（`ReminderPrefs`），只有三个短小的值，
  为此引入 DataStore 属于过度设计；词库导入等复杂配置再交给 DataStore。

## 5. 关键 UI 设计

- 复习卡片（`fragment_review.xml`）：`MaterialCardView` + 大字单词 + 音标，点「显示答案」后展开释义/例句/当前间隔，
  三档按钮才出现——保证反馈基于回忆而不是刚看到的释义。
- **操作区必须锚在固定容器上**：卡片底边约束到 `actionBar`（一个始终存在的 `FrameLayout`），
  而不是某个会被 `GONE` 的按钮；否则按钮一隐藏，带 `elevation` 的卡片会铺满到底部并把按钮盖住
  （本项目真实踩过，见 README 踩坑记录 3）。
- 统计柱状图：**已实现为自绘 `WeekChartView`**（`onDraw` + `Canvas.drawRoundRect`，7 天数据来自 DAO），
  未引入 MPAndroidChart：7 根柱不到 100 行代码，省掉约 300KB 依赖与主题配色冲突的调试成本。
  该 View 同时设置 `contentDescription`（「近 7 天复习量：11/6 2 个，…」），读屏与 UI 自动化都能拿到数据。
- 空态：列表页用 `emptyText` 显隐；复习页用 `statusText` 区分「今天没有到期词」与「本轮复习完成」（靠 `total` 判断）。

### 5.1 统计口径（决定界面数字能不能对得上）

- **算哪些记录**：只算 `review_records`（用户真正点了「认识/模糊/不认识」的那一下），测试模式的作答不计入——
  否则「随便做十道选择题」就会污染连续打卡与正确率。
- **正确率**：`grade >= 1`（模糊、认识）都算通过，只有「不认识」算错。理由：本 App 的三档是「回忆难度」而不是
  对错二元，模糊但想起来仍属于有效记忆；这条规则写在 `StatsCalculator.PASS_GRADE = 1`，改口径只改一个常量。
- **连续打卡**：按**本地日**切分（`Calendar` 取当天 00:00，minSdk 24 不引 `java.time`）。今天有记录就从今天往回数，
  今天还没复习就从昨天往回数——避免「早上打开 App 看到连续 0 天」的挫败感。
- **读取策略**：进入统计页时一次性查最近 60 天记录并重算（`onResume` 触发），**不用 Flow 订阅**：
  复习页连续翻卡时数据库每写一次都会重算整页统计，是明显的浪费；统计页停留时间短，进入时算一次足够。

### 5.2 测试模式（`domain/quiz/QuizBuilder.kt`）

- **两种题型**共用一套出题结构**：`QuizQuestion(word, options, correctIndex)`；选择题从同词库取 3 个**不同**释义做干扰项
  并打乱顺序，拼写题给出「首字母 + 字母数」提示，判定忽略大小写与首尾空格。
- **测试不写库**（重要设计决定）：测试模式只返回成绩与错词列表，**不修改 `words` 的 SRS 字段、也不写 `review_records`**。
  测试是自测手段，若它推进调度，用户随手刷一遍就能把词「刷」到很久以后；错词要进队列应走复习页的「不认识」。
  结果页给出「错词：…，建议去复习页把它们标成不认识」，把决定权交回用户。
- 题量 `DEFAULT_COUNT = 10`、选项数 `OPTION_COUNT = 4`，词库不足 4 词时选项按实际数量降级（不塞空串占位）。
- 单元测试 `QuizBuilderTest`：题数上限、选项唯一性、去重、同种子可复现、不足 4 词、拼写判定（6 个用例）。

## 6. 风险与对策

| 风险 | 对策 |
| --- | --- |
| 导入文件格式不统一 | 先只支持 CSV + 固定 JSON schema，界面上给出模板下载 |
| 通知在工作日/周末行为不同 | 设置页提供「仅工作日」开关，DataStore 存储 |
| 复习队列过长导致体验差 | 每日上限 + 「先复习逾期最久的」排序 |
| 时间与时区变化导致到期计算错误 | 统一存 UTC 毫秒时间戳，展示时用 `LocalDate` 本地化 |
| 伴生模块与主 App 数据库耦合过紧 | 伴生模块只读 DAO，写操作全部走主 App |
